## 四、关键决策与理由

1. **为什么做这个产品**：泰山学院每年开学季，新生问题高度重复且分散（报到/宿舍/选课/资助），老生被重复提问淹没。信息差真实存在，且我就在现场，能触达真实用户。
2. **MVP 为什么只做三个功能**：FAQ 问答 + 多轮上下文 + 诚实兜底。砍掉了账号系统、群机器人、RAG——原则是"先验证 AI 答得准不准，再谈规模化"。
3. **为什么用混元 API**：①目标岗位团队的产品线，深度使用是差异化竞争力；②有免费额度，零成本启动。
4. **为什么先 H5 后小程序**：H5 两天上线，抢开学季窗口；小程序 ICP 备案要 1-3 周，会错过窗口。获客效率的短板等验证需求后用小程序补。
5. **为什么 FAQ 用通用标准而非逐条核对学校真实规定**：速度优先——先把覆盖面做全，让数据（高频问题）告诉我们哪条值得精准化。这是取舍，不是疏忽。
6. **为什么内网穿透起步、云服务器承接**：内测期人少可控，零成本先跑；正式推广后切云服务器解决 7×24 在线。

## 五、踩坑与修复记录

| 坑 | 现象 | 修复 | 学到什么 |
|---|---|---|---|
| 检索泛词抢分 | "军训什么时候开始"错答成报到 | 泛词降权 + 实词阈值 | 关键词匹配要防常见词噪音 |
| 兜底规则太绝对 | "我刚才问了你什么"被拒绝（答案在历史里） | 兜底前先查对话历史 | 规则设计要考虑多轮场景 |
| 服务端编码未防护 | 坏编码请求直接把服务搞崩 | 解码异常返回 400 | 边界输入不能搞崩服务 |
| bat 中文编码 + 引号嵌套 | 双击启动闪退 | 重写纯 ASCII + 标准换行 | Windows 脚本的编码坑 |
| cpolar 免费版地址漂移 | 每次重启公网地址变 | 启动脚本 + 当天拿地址 | 免费方案的不稳定性要写进 SOP |

## 六、数据驱动迭代案例

**第一轮（9.6）**：日报显示满意率 52%、差评 19 条。
- 分类：3 条是历史修复记录；7 条检索错配（问题表述 ≠ 关键词，如"饭卡充钱"错配学费条目）；9 条知识缺口（学生证、校医院、入党、实习等新生高频问题）
- 处理：修 7 处 keywords、新增 11 条知识、3 条政策类条目用官方信息核实（入党流程、普通话等级、学生票新政）
- 验证：17 条差评问题回归测试全部命中正确条目

这个故事证明：我建立了"埋点 → 日报 → 差评分类 → 修复 → 回归"的完整闭环，不是做完就扔。

## 七、如果重来一次，我会……

1. **埋点从第一天就上**：上线第一天就应有数据意识，而不是第二天补——白白丢了第一天的数据
2. **FAQ 关键词设计先做用户语言测试**：让同学用自己的话问问题（"饭卡充钱"而不是"校园卡充值"），关键词按真实表达设计
3. **推广动作要前置准备**：渠道、文案、群资源提前就位，开学第一天就能发；内测不需要完美，有反馈才叫内测
4. **满意度要能定位到具体问答**：现在的满意率只能算整体，不能精确知道"哪一类回答让人不满意"——V2 要补问答级关联

## 八、下一步（V2 方向）

- 问答级满意度关联（知道哪个答案差）
- RAG 升级：关键词检索 → 向量语义检索（"寝室"能命中"宿舍"）
- 长期记忆：记住用户问过什么、是哪个学院
- 微信小程序化（获客效率）
- 部署切腾讯云服务器（7×24 + 固定域名）
